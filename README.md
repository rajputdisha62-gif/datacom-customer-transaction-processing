# datacom-customer-transaction-processing
Python-based customer and transaction data processing project with validation, reporting, logging and unit tests

# Customer Transaction Data Processing

A small Python program that reads customer and transaction CSV files, calculates
customer metrics, and creates JSON reports and customer-data exports.

## 1. Project Overview

The project is centered on `process_data.py`, which defines the `DataProcessor`
class and runs the data-processing pipeline when executed as a script. It reads
`customers.csv` and `transactions.csv` from the current working directory.

The script keeps customer and transaction data in memory while it runs. It
generates three JSON reports, exports customer records in CSV and JSON formats,
and writes log messages to the terminal and `error.log`.

## 2. Project Objectives

- Load customer records and transaction records from CSV files.
- Calculate totals and category-level transaction counts.
- Find customer records matching a case-insensitive substring.
- Generate reports and customer exports in the existing formats.
- Validate required input fields and fail safely on invalid data.
- Avoid processing an identical transaction more than once.
- Make processing and output failures visible through logging.

## 3. Technologies Used

- **Python 3** — application language.
- **Python standard library only**:
  - `csv` for CSV input and output.
  - `json` for reports and JSON export.
  - `logging` for terminal and file logs.
  - `datetime` for report timestamps.
  - `heapq` for selecting the 10 highest-spending customers.
  - `math` for checking that transaction amounts are finite.
  - `unittest`, `tempfile`, and related standard-library modules for tests.

There is no third-party package dependency or dependency manifest in the
project.

## 6. Input Data Description

Both CSV files must be in the current working directory when the program is
run. The source code expects the following column names.

### `customers.csv`

Required columns:

| Column | Description |
|---|---|
| `customer_id` | Identifier used as the key for a customer record |
| `name` | Customer name |
| `email` | Customer email address |
| `join_date` | Customer join date, retained as text |

### `transactions.csv`

Required columns:

| Column | Description |
|---|---|
| `transaction_id` | Unique transaction identifier |
| `customer_id` | Customer associated with the transaction |
| `amount` | Amount parsed as a finite Python floating-point number |
| `date` | Transaction date, retained as text |
| `category` | Transaction category |

The script checks that required headers and values are present. It does not
validate date formats or require amounts to be positive. Files are opened using
Python's default text encoding for the running environment.

## 7. How the Data Processing Workflow Works

When run directly, `main()` performs these steps:

1. Creates a `DataProcessor` configured to read `customers.csv`.
2. Loads and validates customer rows into a dictionary keyed by customer ID.
3. Reads and validates transactions from `transactions.csv`.
4. Skips identical duplicate transaction IDs and rejects conflicting IDs.
5. Updates known customers' spending totals and transaction counts.
6. Writes the customer summary, metrics, and transaction reports.
7. Exports customer data to CSV and JSON.
8. Logs success only if all report and export operations succeed.

`DataProcessor.find_matches()` is also available for case-insensitive substring
searches over a customer field. It is not invoked by `main()`.

## 8. Data Validation and Error Handling

- A missing input file, missing required header, blank required value, malformed
  CSV, or unreadable file causes the related load/process method to log an error
  and return `False`.
- A transaction amount must parse as a `float` and be finite. Values such as
  `NaN` and infinity are rejected.
- Customer and transaction rows are staged before being applied. If validation
  fails partway through a file, that file does not leave partially applied
  customer or transaction updates.
- A transaction for an unknown customer is retained in the transaction list and
  logged as a warning, but does not update a customer's spending total.
- Report and export methods return `False` and log an error when an output
  cannot be written or a requested report/export type is unsupported.
- `main()` checks each report/export result. It attempts all outputs and logs an
  overall error if any output fails.

The script does not use a command-line parser; input and output file names are
currently fixed in `main()`.

## 9. Duplicate Transaction Handling

Transactions are compared by `transaction_id` and all stored transaction
details: customer ID, parsed amount, date, and category.

- If an ID has already been processed with identical details, the repeat is
  skipped and a warning is logged. This applies both within one input file and
  when the file is processed again.
- If an ID is repeated with different details, processing returns `False` and
  logs a conflict. New rows from that attempted file are not applied.
- Transactions accepted in an earlier successful call remain unchanged when a
  later call fails due to a conflict.

## 10. Generated Reports and Output Files

All output names are fixed in `main()` and are written relative to the current
working directory.

### JSON reports

- **`customer_summary.json`** — an object with `generated_at` and `customers`.
  `customers` is a list of customer records. Because the source builds this list
  from dictionary values, customer IDs are not included in these report records.
- **`metrics.json`** — an object with `generated_at` and `metrics`. The metrics
  object contains `total_customers`, `total_transactions`, `total_revenue`,
  `average_transaction_value`, `top_customers`, and `category_breakdown`.
- **`transactions.json`** — an object with `generated_at` and `transactions`,
  containing the accepted transaction records.

Report timestamps use the machine's local time via `datetime.now().isoformat()`.

### Customer exports

- **`customers_export.csv`** — a header row containing `customer_id` and
  customer-record fields, followed by one row per customer.
- **`customers_export.json`** — a JSON object keyed by customer ID.

### Metric behavior to note

`category_breakdown` counts transactions per category. `total_revenue` sums
spending for known customers only, while `total_transactions` includes accepted
transactions for unknown customers too. Consequently,
`average_transaction_value` divides known-customer revenue by the count of all
accepted transactions. This is the behavior currently implemented.

## 11. Logging Configuration

When `process_data.py` is run directly, `configure_logging()` attaches one
terminal `StreamHandler` and one `FileHandler` targeting `error.log`.

- Both handlers write INFO, WARNING, and ERROR messages.
- Both use the same format: `timestamp - level - message`.
- The file handler uses append mode, so existing log entries are retained.
- Reconfiguration removes and closes handlers previously added by this helper
  to avoid duplicate log messages.
- Importing `process_data` does not configure handlers or open `error.log`.

The log path is relative to the current working directory. Running the program
from another directory therefore writes `error.log` there.

## 12. How to Run the Project

In PowerShell, first change to the directory containing the input CSV files:

```powershell
cd "C:\path\to\Datacom Project"
python process_data.py
```

The script reads `customers.csv` and `transactions.csv` from that directory and
writes the reports, exports, and `error.log` there. Review terminal output and
the log file for processing errors.

## 13. How to Run Unit Tests

Run the test suite from the project directory:

```powershell
python -m unittest -v TEST_CASES
```

The tests use temporary input, output, and log files. They cover successful
processing and exports, invalid or missing input, metrics, searching, report
generation, duplicate handling, failure logging, and logging to both
destinations. Temporary files are cleaned up after each test.

## 15. Key Features and Improvements

- Required CSV headers and non-blank values are checked before processing.
- Transaction amounts are parsed once and checked for finiteness.
- Input files are applied atomically after validation.
- Duplicate transactions are skipped when identical and rejected when
  conflicting.
- The top 10 customers are selected with `heapq.nlargest`.
- Existing report and export formats are preserved.
- `main()` checks report and export outcomes instead of reporting success after
  an output failure.
- INFO, WARNING, and ERROR messages go to both the terminal and an append-only
  log file when the script is run directly.
- The `unittest` suite uses temporary files and requires no third-party test
  framework.
